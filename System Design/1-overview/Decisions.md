# Decisions

This is the decision log for choices that cut across several files. Each component file ends with its own Decisions table for choices that stay inside it.

Every decision here is final for the event. Rows that start with a file name belong to an optional feature and go away with that file.

## How BandIt is built

| Decision | Why | Where it shows |
|---|---|---|
| Safety decisions that matter in the first second are made on the band | a crowd crush or a fall cannot wait for the venue laptop, a radio hop or the internet | [Hardware](../4-devices/Hardware.md), [Safety](../6-features/Safety.md) |
| One SpacetimeDB module is the single source of truth for everything live | many writers and many screens must never disagree about a zone or an incident; reducers are transactions and subscriptions push every change | [SpacetimeDB](../2-data/SpacetimeDB.md) |
| The module and every service are Rust; only the two browser apps are TypeScript | one language for the module and the services, sharing generated types | [Rust-Backend](../3-services/Rust-Backend.md) |
| No reducer calls an external service; slow or external work is a `job` row done by a Rust worker | nothing on the safety path waits on the network | [SpacetimeDB](../2-data/SpacetimeDB.md), [Rust-Backend](../3-services/Rust-Backend.md) |
| Presence is zone-level only | the hardware knows which station marker is loudest, never a position | [Hardware](../4-devices/Hardware.md), [SpacetimeDB](../2-data/SpacetimeDB.md) |
| The design uses the firmware as it is; no firmware changes are proposed | the team is not working on the hardware | [Hardware](../4-devices/Hardware.md) |
| Bands point attendees to an exit with the exit colour and, on full bands under low visibility, vibration | the bands have no compass; colour and vibration work in smoke and noise | [Safety](../6-features/Safety.md) |
| Every station marker stands at an exit of the venue as its exit marker and glows that exit's colour; each zone has exactly one station marker (`zone.station_id`) and one exit colour (`zone.exit_colour`) | a band's zone is the station id it hears loudest, so its zone's exit is its nearest door, and "follow your colour" leads there; if a station marker loses power, its bands hear the next-nearest door's station marker instead | [Hardware](../4-devices/Hardware.md), [Safety](../6-features/Safety.md) |
| (TBD -- LEO) Exit routing sends each zone's bands and exit marker the zone's exit colour, sends a crowded zone's bands to the nearest calm zone's door, and routes around a closed door, all through the `command` table | attendees walk to the nearest open door, away from the crowd, and routing adds no new path to the radio | [Safety](../6-features/Safety.md) |
| Organizers send every band command except low visibility from the SpacetimeDB command line; the only band control in the organizer portal (/organizer) is the low-visibility button | the venue needs one button in fire or smoke; the rest are setup and rehearsal tools | [Organizer-Portal](../5-apps/Organizer-Portal.md), [Safety](../6-features/Safety.md) |
| Each component lives in its own file and optional ones can be deleted | the team can drop a feature late without untangling the rest | [README](../README.md) |
| The design follows a few happy paths; an edge case stays only if it protects a person, judges see it at the event, or it wins a sponsor track | a hackathon project is judged on what works end to end | every file |
| Diagrams are Mermaid, rendered and checked before commit | GitHub renders them inline and they diff as text | [README](../README.md) |

## Deployment

| Decision | Why | Where it shows |
|---|---|---|
| The `band1t` module runs on SpacetimeDB Maincloud only; there is no standalone fallback | one deployment means one set of identities, one host and no switch-over during the event | [Architecture](Architecture.md), [SpacetimeDB](../2-data/SpacetimeDB.md) |
| The venue laptop gets internet from a team phone's hotspot | venue Wi-Fi is the least reliable link at a hackathon, so it is off the critical path | [Architecture](Architecture.md) |
| `bandit-api`, `bandit-workers` and `bandit-indexer` run on one always-on Vultr VM as systemd services, behind Caddy; `bandit-api` also serves both web apps from the same HTTPS origin, band1t.vip | judges use their own phones on one public host written into the NFC tags, and the services keep running when the venue laptop sleeps | [Rust-Backend](../3-services/Rust-Backend.md) |
| Blobs are files in `/var/lib/bandit` on that VM, next to the service identities | one machine, no bucket to configure | [Rust-Backend](../3-services/Rust-Backend.md) |
| The venue laptop runs only what needs it: `band1t-bridge` (USB to the gateway), the organizer portal and the SpacetimeDB command line; Test-Bands.md: the `bandit-claims` command-line tool; Vision.md: the recorder, the security view and `bandit-vision` (TBD -- LEO); Bright-Data.md: `bandit-ingest` before the event | the gateway cable and the security camera are physically there | [Architecture](Architecture.md) |

## Identity and attendee data

| Decision | Why | Where it shows |
|---|---|---|
| An attendee claims a band by tapping its sticker and pressing its button | one gesture the attendee learns once, and it proves they hold the band | [Tap-Page](../5-apps/Tap-Page.md) |
| People see a band by its code, such as `K3QX-9A7M`, in its tap link and on every screen, never by its id | a typo fails the code's check character instead of opening someone else's band, and the module and the web pages compute the same code from the id | [Tap-Page](../5-apps/Tap-Page.md) |
| During the event the tap page (/t/code) is band setup, then a thank-you screen ("You're all set", "Thanks, <name>. Enjoy <venue>." and "Keep your band on. After the event, tap it again for your recap: where you went, who you spent time with, and your photos."); it shows no band status, zones, exit colours, wallet balance, profile, graph, schedule or photos. A later tap during the event resumes setup at the first step not yet finished, or shows the same thank-you once every step is done. It has no staff views: staff, medics included, work in the organizer portal. Safety guidance reaches the attendee only through the band | the band carries every safety cue on the wrist, and the night comes back in the recap, so the page has nothing to show in between | [Tap-Page](../5-apps/Tap-Page.md) |
| One sign-in for attendees and staff: the SpacetimeDB SpacetimeAuth magic link, at the first tap, and no other providers; the identity comes from the ID token's issuer and subject | the same person is the same identity on every device; BandIt keeps no password and no email address | [Tap-Page](../5-apps/Tap-Page.md), [SpacetimeDB](../2-data/SpacetimeDB.md) |
| There is no recap email: the "Event ended" press (`end_event`, role `ops`) turns every open tap page into the recap live, and the tap link `/t/{token}` reopens it later for the band's signed-in owner | one press by an organizer ends the night for everyone; the band's own URL is the way back | [Tap-Page](../5-apps/Tap-Page.md), [Organizer-Portal](../5-apps/Organizer-Portal.md) |
| There is no separate role for running the event: an organizer is a staff member with `ops`, which runs `end_event`, `reopen_event` and the organizer portal's attendee list and "Event ended" button; only `owner`, the identity that published the module, grants roles: service roles with `grant_role` and `revoke_role` from the SpacetimeDB command line, and staff by email with `add_staff` on the organizer portal's Staff tab, which only the owner sees; the people staff roles are `ops` and `medic`, plus Social.md's `photographer` | one role runs both the venue and the organizer portal's event controls, every grant comes from one identity, and no other staff screen can widen anyone's access | [SpacetimeDB](../2-data/SpacetimeDB.md), [Organizer-Portal](../5-apps/Organizer-Portal.md) |
| Social.md: attendees type their own social handles at onboarding, Meta only (Instagram, Facebook, Threads) | no verification flow to build; Meta is the sponsor track; people's social profiles are never scraped | [Social](../6-features/Social.md) |
| Social.md: there is no company field at onboarding; `works_at` comes from the import and a claimed profile | one less form field, and the company is already known for exhibitors and speakers | [Social](../6-features/Social.md) |
| Test-Bands.md: each crowd band (from 100; 1,000 at the event) is worn by a generated attendee with a made-up name and an Instagram handle made from it, created by `start_crowd` inside the module; the safety path reads only bands 1 to 99 | the venue map and the big-screen people graph show a real-looking crowd, through the same social step as real bands, and the crowd never opens an incident | [Test-Bands](../3-services/Test-Bands.md) |
| Bright-Data.md: an attendee who already owns a band claims their scraped profile by picking it at onboarding; `claim_person` refuses anyone who owns no band | the band claim's press is the proof, so there is no second press and no email round trip | [Bright-Data](../7-integrations/Bright-Data.md) |

## Sponsors and external services

| Decision | Why | Where it shows |
|---|---|---|
| SpacetimeDB holds live state and every write, and decides who and what is on every list; Elastic.md: Elastic, the Evidence Engine, holds the raw scraped data, organizes it into the event setup, orders the recap's suggestions by meaning and finds past claims as precedents, and never holds live state | each database is used for the problem it solves best | [Architecture](Architecture.md) |
| Social.md: the people graph's links live in SpacetimeDB, and there are no links between people who never met | measured links are exact, private and change live | [Social](../6-features/Social.md) |
| Social.md: the big screen draws the event graph in 3D with the event photos among the people the bands put in them; every person shows by display name, and the photos come from the staff view `board_photos` as node ids | everyone in the venue watches the night take shape and sees who met whom, photos included | [Social](../6-features/Social.md), [Organizer-Portal](../5-apps/Organizer-Portal.md) |
| Elastic.md: there is no typed search. The recap's people and booths come from `GET /api/recap`, which `bandit-api` builds from SpacetimeDB's `social_*` views; Elastic only orders them, with semantic queries on `bandit-people` and `bandit-booths`, and the order is logged to `bandit-recap-rankings` for Elastic Kibana | the recap is the product, and a list the bands measured is exact and private; meaning only changes the order | [Elastic](../7-integrations/Elastic.md), [Tap-Page](../5-apps/Tap-Page.md) |
| Elastic.md: `bandit-organize` in Elastic Workflows is the only path that organizes the scraped data; a failed run loads the last good bundle | one path to explain and to show judges; the saved bundle means the event never waits on a failed run | [Elastic](../7-integrations/Elastic.md) |
| Elastic.md: one Elastic Agent Builder agent, `bandit-organizer`, decides the scraped organisations that no exact match settles, reading the records through its Elastic ES\|QL tools `bandit.records` and `bandit.candidates`; judgments about claims, medical PDFs and venue setup go to the Anthropic Claude API | each model does one kind of work | [Elastic](../7-integrations/Elastic.md), [Anthropic-Claude-API](../7-integrations/Anthropic-Claude-API.md) |
| Elastic.md: the team shows the Elastic side in Elastic Kibana (Elastic Workflows runs, Elastic Agent Builder, and two dashboards that `bandit-ingest` installs: the scrape pipeline and the sponsors and prizes; Insurance.md: the claims evidence dashboard) | it is the most visual way to show how the scraped event was organized and who backs it, and it never repeats the live organizer portal | [Elastic](../7-integrations/Elastic.md) |
| Anthropic-Claude-API.md: every Anthropic Claude API call goes through `claude-client`, on one model set there | one client, one model, every call recorded | [Anthropic-Claude-API](../7-integrations/Anthropic-Claude-API.md) |
| Bright-Data.md: the import fetches everything through the Bright Data Web MCP, from the sources in the event's folder (`sources.json`): `scrape_as_markdown` for the event's pages, and `run_scraper` on the Bright Data Web Scraper API datasets for the sponsors' LinkedIn and Crunchbase records and the venue's Google Maps place; Cal Hacks 13.0 is the first event it runs at | one product and one token for pages, company facts and the venue's place; only the event folder changes from one event to the next | [Bright-Data](../7-integrations/Bright-Data.md) |
| Bright-Data.md: the 3D venue model is exported once, before the event, from the Cal Hacks venue map through the Bright Data Browser API, and kept as a file | the export runs a script inside the map's page, which needs a full remote browser; with the file kept, nothing at the event waits on Bright Data | [Bright-Data](../7-integrations/Bright-Data.md) |
| Bright-Data.md: booth positions are data: a spot per sponsor in `booths.json`, else its default spot, and the 3D venue's sponsor tables matched to booths by name with `load_venue_spots`; a misplaced booth is fixed by hand with `place_booth`, and a re-import keeps it | the event's pages give no booth positions, so the team keeps them where it can check them, and a fix by hand survives every re-import | [Bright-Data](../7-integrations/Bright-Data.md) |
| Merch.md: merch is a few templates the team makes by hand before the event, with the attendee's own photo placed in each template's photo area by the app; no image API and no image generation anywhere | no AI or server rendering on the path to a sale, and any event loads its own templates | [Merch](../6-features/Merch.md) |
| Capital-One-Nessie.md: nothing is paid at the venue; each attendee gets a $200 Capital One Nessie sandbox wallet when they tap "Connect" on "Connect your Capital One wallet", the last setup step, buys merch from it with one tap (`buy_merch`) after the event, and receives settled claims into it; the balance is the module's own sum of `wallet_entry`, because the sandbox never moves a balance | the README moves shopping to after the event; the claim payout landing on its own is what judges see of Capital One Nessie; one tap with an exact balance check needs no confirm screen | [Capital-One-Nessie](../7-integrations/Capital-One-Nessie.md) |
| Insurance.md: insurance runs as the insurance Decision Engine, which learns from the organizer. The medic files the claim during the event; a claim that no learned rule settles waits for the organizer (`ops`), who decides it after the event; each approval with learn on becomes a rule that settles the next similar claim on its own. Code checks the facts and computes money, and the Anthropic Claude API reads the bill and explains causation. Only code at claim open (disputed evidence, a staff claimant, no cover, a zero payout) and the organizer refuse a claim; the Anthropic Claude API's review and Elastic's validation only flag and route it. A mass occurrence turns auto-settle off and sends every claim of it to the organizer. An accuracy run on planted claims gives the scorecard, and the edge cases (stale approval, witnesses in another zone, injury at home, re-scanned duplicate bill, staff claimant, refusal after reserve, a reconciliation difference) are shown, not described | the finance track judges a system that decides money on its own and can prove it is right; two staff roles are enough, the medic during the event and the organizer after it | [Insurance](../6-features/Insurance.md) |
| Insurance.md, Elastic.md: similar past claims come back from Elastic only as checks, as ids and scores written through a reducer, and never change an amount; the claim copy is de-identified | ranking by meaning is what Elastic does best, and money and live state stay in SpacetimeDB | [Insurance](../6-features/Insurance.md), [Elastic](../7-integrations/Elastic.md) |
| Vision.md: security cameras and models are Leo's call (TBD -- LEO); the other files depend only on the interface | the vision hardware is not settled; the rest of the system does not wait on it | [Vision](../4-devices/Vision.md) |
